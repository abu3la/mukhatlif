## شرط سابق قبل نافذة الويكند

أداة الجرد الحالية Read-only، و`--apply` مقفول عمدًا. قبل التنفيذ يجب إضافة
مرحلة apply واختبارها محليًا. لا يكفي تشغيل الخيار الحالي؛ فهو سيرفض التنفيذ.

يجب أن يحقق apply هذه الضمانات:

1. تحديد دفعة صريحة بالمعرّفات، دون اختيار ضمني لكل المكتبة.
2. تنزيل ملف واحد في كل مرة إلى مجلد خاص بصلاحية `0700` وملف `0600`.
3. التحقق من الحجم وSHA-256 وmagic bytes والصيغة قبل الرفع.
4. استخدام المفتاح الحتمي الموجود في التقرير:
   `legacy/podcasts/source/<source-url-sha256>.<ext>`.
5. عدم استبدال أي object موجود ومختلف.
6. تنزيل object من R2 بعد الرفع ومقارنة الحجم وSHA-256.
7. تحديث `episodes.audio_key` بعد نجاح التحقق فقط.
8. استخدام compare-and-set يتأكد أن `audio_key` ما زال فارغًا وأن
   `audio_url` و`source_url` و`rss_guid` لم تتغير.
9. كتابة checkpoint ذري بعد كل حلقة ليستأنف التشغيل دون تكرار.
10. توفير `--resume` و`--batch-file` و`--confirm-report-sha256` بدل فتح apply عام.

بوابة المراجعة قبل الويكند:

```bash
pnpm test:audio-r2
pnpm type-check:audio-r2
pnpm exec eslint tools/audio-r2/src
pnpm exec prettier --check tools/audio-r2
git diff --check
```

يجب أن تضاف اختبارات upload/verify/CAS/resume/failure، وألا يفتح القفل إلا بعد
مراجعة الكود وصدور موافقة جديدة صريحة من المستخدم.

## التحضير قبل التنفيذ

قبل بدء أول دفعة في نافذة الويكند:

1. إعادة توليد dry-run وفحص أن النتيجة ما زالت 836 ready و0 blocked.
2. إعادة فحص المصادر بـHEAD ومقارنة SHA التقرير المراجع.
3. أخذ نسخة احتياطية جديدة من Supabase وتوثيق SHA-256 ونجاح
   `pg_restore --list`.
4. التحقق أن حاوية R2 الصحيحة خاصة وليست لها `r2.dev` أو custom public domain.
5. التحقق أن مساحة القرص المؤقت لا تقل عن 2 GiB؛ أكبر ملف 640 MB تقريبًا.
6. تشغيل الجهاز على طاقة ثابتة واتصال سلكي، وتعطيل sleep طوال الدفعة.
7. التأكد أن روابط Anchor الأصلية تعمل وأن الموقع والتطبيق يشغلان عينة منها.
8. تسجيل وقت البدء، منفذ التنفيذ، مسار checkpoint، وSHA ملف الدفعة.

أوامر القراءة الآمنة الحالية:

```bash
pnpm migrate:audio:r2
pnpm migrate:audio:r2 -- --head-sources
```

هذه الأوامر لا ترفع ولا تعدل Supabase.

## دورة معالجة الحلقة

لكل حلقة، بالترتيب:

1. قراءة snapshot المراجع والتأكد من عدم تغير بيانات المصدر في Supabase.
2. تنزيل الملف من Anchor/CloudFront إلى ملف مؤقت.
3. حساب الحجم وSHA-256 والتحقق من MP3/M4A عبر magic bytes.
4. HEAD للمفتاح الحتمي في R2.
5. إذا كان المفتاح مفقودًا: رفعه مع Content-Type الصحيح وmetadata غير حساسة.
6. إذا كان موجودًا: لا يستبدل؛ يتحقق منه أو تتوقف الحلقة كـconflict.
7. تنزيل النسخة من R2 مباشرة وحساب SHA-256 والحجم.
8. عند التطابق فقط: CAS لتعبئة `episodes.audio_key` مع إبقاء `audio_url`.
9. smoke لمسار API للصوت: Full request وRange request.
10. تحديث checkpoint وحذف الملف المؤقت فقط بعد حفظ النتيجة.

## شروط التوقف الفوري

تتوقف الدفعة ولا تبدأ التي بعدها عند أي من الحالات التالية:

- اختلاف حجم أو SHA-256 بين المصدر وR2.
- فشل magic bytes أو صيغة غير MP3/M4A.
- تغير `audio_url` أو `source_url` أو `rss_guid` أو ظهور `audio_key` جديد.
- محاولة overwrite أو تعارض object قائم.
- خطأ مصادقة Cloudflare/Supabase أو اختيار account/project/bucket مختلف.
- امتلاء القرص أو انقطاع checkpoint.
- أخطاء شبكة متكررة لثلاث محاولات مع backoff.
- نسبة فشل تتجاوز 1% من الدفعة.
- فشل Range أو إرجاع محتوى غير صوتي من API بعد الربط.

## الاستئناف والرجوع

- الاستئناف يقرأ checkpoint ويعيد التحقق من object الموجود؛ لا يعيد رفع عنصر
  verified ولا يتخطى conflict.
- لا تحذف R2 objects أثناء نافذة الترحيل.
- لأن `audio_url` يبقى محفوظًا، الرجوع التشغيلي يكون بإزالة `audio_key` عبر
  CAS للحلقات الموجودة في تقرير الدفعة فقط، ثم يعاود API استخدام الرابط الأصلي.
- لا ينفذ rollback جماعي يدويًا. يجب أن ينتج apply ملف rollback دقيقًا لكل دفعة
  ويختبره قبل التنفيذ.

## التحقق بعد كل دفعة

- العدد المخطط = uploaded/verified + already-verified + conflicts + failures.
- 0 object ناقص و0 checksum mismatch.
- كل `audio_key` في Supabase يشير إلى object verified.
- كل `audio_url` الأصلي ما زال موجودًا.
- Full GET يعيد صوتًا صحيحًا.
- Range يعيد `206` و`Content-Range` صحيحًا.
- الحلقة العامة تعمل في الويب والتطبيق.
- الحلقة الحصرية التجريبية ترفض غير المشترك وتعمل للمشترك.
- حفظ تقرير خاص بالدفعة خارج Git بصلاحية `0600` مع SHA-256.

## الزمن والتكلفة التقريبية

التحقق الكامل يمرر البيانات ثلاث مرات: تنزيل المصدر، رفع R2، وتنزيل R2 للتحقق.
إجمالي حركة الشبكة المتوقعة 441,544,247,184 بايت، أي نحو 411.22 GiB.

- 50 Mbps: نحو 19.6 ساعة نظريًا.
- 100 Mbps: نحو 9.8 ساعات نظريًا.
- 200 Mbps: نحو 4.9 ساعات نظريًا.

يضاف وقت retry والكتابة والـhash والفحوص؛ لذلك يخصص الويكند كاملًا ولا نعتمد
الزمن النظري كموعد انتهاء.

تخزين 147.18 GB على R2 Standard يكلف قرابة $2.06 شهريًا بعد 10 GB المجانية،
إذا كانت الحصة المجانية غير مستهلكة. عمليات هذه المكتبة الأولية تقع غالبًا تحت
الحصة المجانية، وR2 لا يفرض رسوم egress مباشرة. لا يشمل التقدير ضريبة الفاتورة
أو أي bandwidth قد يمر عبر Hostinger.

## قرار Go / No-Go في الويكند

لا يبدأ apply إلا بعد تحقق كل ما يلي:

- [ ] نسخة Supabase الاحتياطية الجديدة موثقة ومتحققة.
- [ ] apply implementation واختباراته مراجعان وكل الفحوص خضراء.
- [ ] dry-run وHEAD حديثان: 0 blocked و0 mismatch و0 error.
- [ ] الدفعة الأولى محددة في ملف ثابت وله SHA-256.
- [ ] الحساب والمشروع والحاوية مطابقون لقيم Development أعلاه.
- [ ] R2 خاص، وAnchor ما زال يعمل كمسار رجوع.
- [ ] اتصال وطاقة ومساحة مؤقتة كافية.
- [ ] صدرت موافقة صريحة جديدة من المستخدم على الدفعة المحددة.

إذا غاب أي شرط فالقرار No-Go، وتبقى المكتبة تعمل من Anchor دون تغيير.
